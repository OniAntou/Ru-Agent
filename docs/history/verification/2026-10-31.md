# Verification evidence - 2026-10-31

Historical snapshot only. These results describe the recorded working tree and
conditions, not current acceptance. See [current verification](../../operations/verification.md).

## Tool read ergonomics

A model reads an empty `read` page as a broken tool. `read` and `read_file` now
carry a `notice` that names the actual situation: the file exists but is empty
(0 bytes), the requested `offset`/`start_line` is at or past the end (with the
real byte or line count), or content remains and where the next page starts. A
page cut by the output budget says so and points at `next_offset` instead of
ending on a bare `truncated` flag. `read` also reports `estimated_tokens` for the
returned content, so the model can budget in the unit it is billed in.

`FileReadOutputBudget` now reserves 256 bytes for fields added after fitting, so
notice and estimate cannot push the envelope past the 4 MiB cap. The
`ModelToolHeadroomRegressionTests` case caught that before the reserve existed.
The two changed tool descriptions updated the tool-contract golden lock
deliberately (description SHA-256 rows for `read` and `read_file`).

Broker 1,445 tests passed for this change in isolation (`FileReadAdapterTests`,
`FileLineReadTests`, headroom and tool-contract tests included).

## Tool telemetry counters

The comparison with Claude Code's read tool showed a measured dedup win (18% of
reads were same-file collisions). Ru now measures the same question before
changing behaviour: the Broker source emits `ru.tool.calls`
(`tool.id`, `tool.status`, `error.code`) and `ru.tool.read_pages`
(`tool.id`, `repeated`). `repeated` is answered by a bounded per-service path
tracker that never withholds content; a real "file unchanged" answer needs the
Host's compaction-aware read state, so dedup stays a separate decision.

The Host's meter provider now adds the Broker source, without which the counters
would be produced but never collected. Tags follow the existing allowlist:
bounded tokens only, never paths or arguments. Two listener tests pin the first
read (`repeated=false`), the second (`repeated=true`) and a failed call's status
and bounded error code.

## Model persona names the model, not the product

Asked which model it was, the model answered "Ru Agent". The cause was the first
sentence of the core contract: "You are Ru Agent". The environment block already
carried the serving model id, but it read as metadata next to a first-person
identity claim.

The persona block now opens with that id - "You are <model>, a coding model
running inside Ru Agent" - states that Ru Agent is the host product and not the
speaker's name, and requires model or version questions to be answered with the
id from the environment block. The product name in the GUI and terminal is
unchanged; only the model-visible identity moved. A test pins the identity
sentence and that "You are Ru Agent" no longer appears in the contract.

## Model-visible git_status tool

Handoff item 1 landed: `git_status` is a Broker-bound, read-only
`workspace.read` tool. One fixed `git status --porcelain=v2 --branch` invocation
runs through `IGitCli` and the existing `GitStatusParser` (no second parser),
with `status.relativePaths=true`, `--ahead-behind`, `--untracked-files=normal`
and a `-- .` pathspec, so a workspace that is a subdirectory of a larger
repository reports only its own subtree with workspace-relative paths. The
report separates `staged`/`unstaged` (porcelain code plus `original_path` for a
rename), `untracked` and `unmerged`, carries `truncated`, `unparsed_lines` and
`clean`, and answers `is_repository: false` with a notice outside Git instead of
failing the call. It is in `coding_v2`, `patch_v2` and `coding_code_v1` (now
27/26/29 definitions; catalog 29, Broker bindings 28), is not rememberable for
approval, and is not in `SubagentRoleTools`.

Policy identity was the non-obvious seam: `PolicyContextFactory` rejects an
unlisted id as `malformed_call`, so an executor alone would have been denied
before dispatch. `git_status` is registered there as a target-free `read`
context, and a test pins that `plan` (the read-only preset) still allows it.

## Park reasons in words, and one more self-repair

read "Waiting for confirmation" and the status line showed
`provider_transport_error`. Park reasons now resolve through one shared catalog
(`AgentParkReasonCopy`), used by the GUI activity row, the GUI status line and
the TUI notice. A transport failure reads "network connection to the provider
failed", a timeout "the provider stopped responding", a spent window "the run
used its model step budget"; the raw code stays beside it in the tooltip and the
terminal notice. The summary-to-status assignment also skips raw state tokens

through them on the way to the sentence.

## Host stop mid-model-step no longer leaves a running run

A GUI session was closed while the provider was still generating. The durable
stream ended with `model.step_started` and no completion, but every dispatched
tool already had a receipt. On the next start the recovery scanner read that as
"simply mid-flight", the drive loop opened another model step on top of the
orphaned one, and the session kept its active-run ownership. New prompts queued
behind a turn whose model was already gone, and reopening the app showed the
session running.

Recovery now tracks the last model step admission against its completion. A
run whose step never completed is failed by name: the scanner commits an
`interrupted` completion for that step and `run.failed` with
`recovery_model_step_incomplete`, releasing the session. A run whose step did
complete still resumes exactly as before.

## Automatic budget windows

A user report made the per-run budget visible: one long prompt could stop at
128 model steps and queue the next prompt behind a Continue. The budget was
never per session - each chat message is a new run with fresh counters - but
stopping a single run was still a pause other agents do not show.

Checked how comparable agents bound one task before changing the policy:

- **Cursor** agent docs: "There is no limit on the number of tool calls Agent
  can make during a task."
- **OpenCode** agent option `steps`: unset means run until the model stops or the
  user interrupts; when set, the limit forces a summary of remaining work rather
  than a Continue button.
- **DeepSeek Harness** (the installed runtime inspected locally): no per-step or
  per-tool budget; long work uses goal rounds (default 256, continued
  automatically), and the goal is blocked with `round-limit` at the cap.
- **Gemini CLI**: `maxSessionTurns` defaults to -1 (unlimited) with loop
  detection.
- **Claude Agent SDK**: optional `maxTurns`; unset has no hard limit.

Ru keeps its fail-closed backstop but no longer stops at the first window. A
root run opens the next window itself, up to **8 windows** (1,024 model steps /
2,048 tool calls) per run; only then does it park with
`model_step_budget_exhausted` / `tool_call_budget_exhausted`. A manual Continue
after that grants one further window, and every later window is manual. Internal
subagent runs never take the automatic path (own 32/64 limits), and the family
pool stays at 128/256 per window. Checkpoint calls use the same window rule.

### Evidence

- `AgentBudgetTests`: auto window opens with reset counters; the automatic cap
  still parks; an internal run never auto-opens; a tool batch opens a window only
  when it fits one.
- `ContextCompactionCoordinatorTests`: a checkpoint at the step limit opens a
  window; format repair follows it; the cap still parks with zero model calls;
  a real model step continues with `BudgetWindow=2` and no `continue.requested`.
